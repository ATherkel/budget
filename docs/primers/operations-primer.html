01

Three kinds of thing, and only two are precious

After this: you can sort any file the platform touches into one of three kinds, and say which kind a backup exists for.

Issues #4 to #8 decided what the pipeline computes. Issue #10 is about running it: a real machine, a real folder, a Sunday when the disk dies. The whole design follows from sorting every file into one of three kinds.

KindExamplesIf it is lost
What the bank saysThe CSV exports you downloadGone, unless the bank still offers that history
What you sayAccounts, categories, rules, manual decisions, and each import’s declared account and datesGone. No one else knows why you called that IKEA purchase a gift.
What the pipeline derivesSilver’s transactions, Gold’s facts, the dashboard’s numbersRebuilt from the other two (ADR-003)

So the design has one principle in two halves: everything you say is kept as text, and everything the bank says is kept as a file. Both live in OneDrive. The databases can then always be rebuilt, and backups exist to make that fast, not to make it possible.

The one sentence

How does the household run this pipeline so that a report is reproducible, a mistake is undoable, and a broken machine is an inconvenience rather than a loss?

02

Three profiles, one code

After this: you can say what separates production, development and test, and why there is no default.

At work there is production and nothing else, so every experiment runs against real tables. Here the three tiers are an explicit learning objective (issue #2), kept apart even where a single household could get by with fewer. They are not three servers: they are three profiles, meaning three configurations of the same code, each naming every path the application may touch.

ProductionDevelopmentTest
DataReal exportsProduction’s latest backupSynthetic fixtures in the repo
Written byPipeline commands onlyYou, experimentingThe test run
LivesForeverUntil the next refreshOne test run
DashboardHome Wi-Fi, with a passwordThis PC onlyNever served

Why nothing picks a profile for you

You would naturally set BUDGET_PROFILE to production in your shell, so that budget import just works. Then you run the test suite in the same shell. If the code fell back to “whatever the environment says”, the tests would open your real database. So:

  1. Every command refuses to run until a profile is named, with --profile or BUDGET_PROFILE.
  2. Test profiles are never files. The test suite builds each one in a temporary folder, ignores BUDGET_PROFILE, and refuses any store path outside that folder.
  3. Every database records which profile it belongs to when it is created. Opening a production store under the test profile is refused, even if a bug hands the test its path.

Three independent guards, because any one of them can be defeated by a single mistake.

03

Extract, clean, conform, deliver: one file per step

After this: you can map Kimball’s four ETL steps onto the stores, including the one place the mapping bends.

Kimball’s ETL Toolkit splits the back room into four steps, extract, clean, conform, deliver, and saves the data after each one (“staging”), so a failure restarts from the last completed step instead of the beginning. You chose to make those saved steps literal: each is its own SQLite file.

Where the mapping bends

In Kimball, conform also builds the conformed dimensions: the account, category and date tables every fact shares. Here Silver conforms each source into one canonical transaction, but the dimensions come from your account registry and taxonomy, so Gold builds them. The conform step is therefore split across two files. The doc says so rather than adding a fourth store.

What staging buys

  • Restart points. A rule change rebuilds Gold only, reading the Silver file as it is.
  • Divergence points. Development can take production’s Bronze and Silver and rebuild only what it changed (module 05).
  • Independent migrations. Each file has its own numbered migrations and schema version, so a Gold change never touches Bronze.

The cost

A Silver write and a Gold write are two transactions, in two files. A crash between them is harmless only because nobody reads Silver: the dashboard still sees the previous Gold publication, and the next command carries on. That is why module 09’s commit point matters.

04

Two folders: one live, one synchronised

After this: you can say which folder each file goes in, and why the live databases must stay out of OneDrive.

%LOCALAPPDATA%\budget\production\      live databases: never synchronised
    bronze.db  silver.db
    gold\catalog.db  gold\publication-000042.db
    scratch\  logs\
OneDrive\Budget\                       closed files only: safe to synchronise
    inbox\joint-current\               drop new exports here
    exports\joint-current\             the archive
    inputs\                            what you say
        accounts.toml  taxonomy.toml  rules.toml
        decisions.jsonl  imports.jsonl
    backups\2026-05-02T18-05-11Z\      backup sets

A SQLite database in WAL mode is three files that change together: bronze.db, bronze.db-wal and bronze.db-shm. A sync client copies files one at a time, whenever it gets round to them. If it uploads the main file from one moment and the WAL file from another, the cloud holds a database that never existed, and SQLite’s own guidance lists exactly this as a way to corrupt one. So (ADR-013) the live stores stay in %LOCALAPPDATA%, which OneDrive does not touch.

Everything in the OneDrive folder is a closed file: an export, a text file you saved, a finished backup. Copying one of those at any moment is safe. That split is what lets OneDrive be the off-site copy of everything precious.

06

Your configuration is TOML, and money is always in quotes

After this: you can write a rule, and explain the one trap TOML sets for money.

format = 1

[[rule]]
id = "r-furniture"
priority = 10
when.description_contains = "IKEA"
when.amount_max = "-1000.00"        # quoted: a decimal string
then.category = "furniture"

[[rule]]
id = "r-savings-transfer"
when.description_contains = ["TO SAVINGS", "FROM CURRENT"]   # any of these
then.transfer_claim = true

Every when condition must hold, and then has exactly one outcome: a category, a transfer claim, or an adjustment with a reason (ADR-011). Python reads TOML with the standard library, so the CLI gains no dependency.

The trap

Write when.amount_max = -1000.00 without quotes and TOML reads it as a binary floating-point number, the same kind that turns 0.1 + 0.2 into 0.30000000000000004. Most of the time the damage is invisible. The platform never accepts one for money, so an unquoted amount is a configuration error that fails the build before anything is published, naming the file and the rule: 

rules.toml: rule "r-furniture": when.amount_max must be a quoted decimal, got a number
1 configuration error. Nothing was built.

Three more guards

  • Unknown keys are errors. A misspelt when.descripton_contains would otherwise make a rule match everything.
  • Every file says format = 1. When the format changes, old files are refused with a clear message instead of being half-understood.
  • budget check validates every file without building, and lists every error at once.
07

Manual decisions: a log you append to through one door

After this: you can say why decisions are not in TOML, how you undo one, and what the “door” is for.

Rules are yours to edit. Decisions are different: PR #57 makes them an append-only log, where a new entry supersedes an old one and nothing is rewritten. That gives an audit trail you can read without a database. 

> budget review
unmatched-transfer  no-candidate
  3f9a2c1e  joint-current  2026-02-16  −1,000.00  TO SAVINGS
> budget decide classify 3f9a2c1e external-saving --reason "To Bo's savings, not imported"
Recorded d-0005. Gold publication 44 is current (was 43).

That appends one line to decisions.jsonl:

{"format": 1, "entry": 5, "decision_id": "d-0005", "recorded_at": "2026-05-03T09:12:40Z",
 "kind": "classify", "targets": ["3f9a2c1e77b0…"], "category": "external-saving",
 "reason": "To Bo's savings, not imported", "supersedes": null}

Why JSON Lines and not TOML

You write rules; the application writes decisions. Python’s standard library can read TOML but not write it, and it can do both with JSON. One JSON object per line also makes “append” literal.

The door

Every decision goes through one validation boundary before it is recorded. Do the targets exist? Does the category? Does a pair’s amount cancel? Does the transaction already have a decision this one fails to supersede? The CLI uses that boundary today. The browser editor that issue #2 says may come later uses the same one, so it inherits every rule instead of reinventing them.

Undo and hand edits

  • To withdraw a decision, record a retract entry naming it in supersedes. It is called retract so it is not confused with withdrawn, which records that the bank removed a transaction.
  • Each build’s recipe stores a hash of the log up to the entry it read. Edit an old line by hand and check notices.

The savings account had no activity for three months. Without a declaration, Bronze would assume the file covers up to the day before it was made, and silently certify February to April as quiet (bronze-layer.md). So it asks, and only then.

If the power goes halfway

Each file is idempotent. Rerun budget import. A file whose account, original filename and bytes already have a stored run is simply finished: archived and cleared from the inbox, with no second run recorded. A genuinely new export of the same bytes has a new date in its filename, so it still counts as the “nothing happened” evidence Bronze wants.

The import log

Your answer 2026-04-30 is something you said, so module 01 wants it as text. Every import appends a line to imports.jsonl with the account, both dates and the archive path. With it, Bronze can be rebuilt from the archive alone (module 10, the worst case).

10

Backups, restore, and the worst case

After this: you can say what a backup set holds, when one is taken, and what survives when every backup is gone.

A backup set is one folder: a snapshot of every store, taken through SQLite’s backup API (never a plain file copy of a live database), a copy of your inputs folder, and a manifest with each file’s hash and schema version. It is written after every import or rebuild that publishes, and before every migration, into OneDrive. The newest 30 are kept, plus the newest of each month.

What went wrongYou runWhat comes back
A bad rule, noticed in the printed diffbudget undoThe previous publication, instantly (PR #57)
The machine diesbudget restore <newest set>Everything. At most the imports since the last set are missing, and every import writes one.
Every backup set is lost toobudget restore --from-archiveEvery report, exactly, from the export archive, imports.jsonl and your inputs. Past views and recipes are lost.

The third row is module 01 paying off. It works only because the import declarations (module 08) and the decisions (module 07) are text in OneDrive, not rows in a database.

Two safety rules

  • restore only writes into a profile with no stores yet. It cannot overwrite a working database by mistake.
  • Every restore ends with verify: SQLite’s integrity check on every file, then a full rebuild into a scratch folder whose result fingerprint must equal the current publication’s. That is PR #57’s “routine proof of reproducibility”, run on the copy you just restored.
11

What the terminal tells you, and what the log never does

After this: you can read an exit code, find the two completeness checks, and say what never reaches a log file.

Exit codes

CodeMeans
0Done. Open review items and quarantined imports are results, not failures: reports may be provisional as long as they say so (issue #2).
1You typed the command wrong.
2Your input was refused: a configuration error, a rejected decision, a refused import. Nothing was published.
3The environment was refused: no profile, the wrong profile’s store, a pending migration, SQLite too old, uncommitted code in production, a locked store.

Two completeness checks, after every command that builds

  • Balances: per account, the latest export, how far the evidence reaches, quarantined imports, and which months are provisional and why.
  • Classification: per account and month, unclassified money in, money out and count, and open review items by kind.

budget status shows the same on demand. It answers “can I trust this month yet?” before you open the dashboard.

The log

Routine logs keep what a fault needs: the command, counts, durations, versions, error codes, and the ids of import runs, publications and decisions. They never hold an amount, a balance, a description, a bank label, an original filename, or a transaction_id, which is a hash of the transaction’s content. A test runs every walkthrough and searches the log for each synthetic amount and description.

Proved outside production first, and the dashboard on your Wi-Fi

After this: you can state the rule a procedure passes before production trusts it, and the one accepted risk on the dashboard.

The rule

A procedure runs in production only after it passed in test and ran at least once in development against a restored production backup.

ProcedureTest, every CI runDevelopment
MigrationsEvery one, from empty and from last release’s storesRehearsed on a fresh refresh first
Import retryA crash injected after each stepReal export shapes, via upstream
PublishingCrash either side of the commit point; undoEvery rebuild publishes
Backup and restoreBackup, restore, verifyEvery refresh is a restore
Restore from the archiveReports come back exactlyOnce before trusting it, then yearly

This is the part meant to carry to work: a test tier built only from synthetic fixtures, a development tier cloned from production’s backups, and production written only by the pipeline.

The dashboard

  • It listens on the home network only; a Windows firewall rule allows the port on private networks. Nothing is reachable from the internet.
  • One household password guards every page. Its hash lives under %APPDATA%, never in OneDrive or the repository.
  • It opens Gold files read-only, and has no route that writes, apart from logging in and out.
  • Accepted risk: it runs over plain HTTP. Someone on the same Wi-Fi who captures traffic could read the password and the pages. HTTPS with a certificate trusted on each phone is the upgrade if that changes.
