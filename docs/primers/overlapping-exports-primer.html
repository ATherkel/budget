Your bank sends the same purchase twice. Now what?

PR #16 and PR #31 are 2,100 lines about one small, genuinely awkward problem. This page walks you through it in fourteen short modules, each with a worked example using real kroner. Tick a module off once you can explain it to someone else. Your progress is saved.

About this file

This is a primer, not a contract. It explains what the documents in docs/architecture/ and docs/decisions/ decide; it never decides anything itself. Where this page and one of those documents disagree, the document is right and this page is out of date — say so and it gets fixed.

It lives in the repository at docs/primers/overlapping-exports-primer.html; that copy opens by double-clicking and needs no server. Your ticks are saved as you go. Current through the second review round, which closes the last six of the ten comments in module 12. Module 14 is what that round found — including one rule the first round got wrong.

The short answer to your question

No, you don't have to merge blind — but you also don't need to understand every sentence in those documents. You need to understand five ideas, and be able to answer five questions. Modules 01–09 are the five ideas. Module 13 is the five questions. Everything after that is what the PRs did, what the reviews caught, and the one rule that turned out to be wrong.

Contents

01

The whole problem, in one picture

After this: you can state the problem both PRs exist to solve, in one sentence.

You log into Danske Bank and ask for a date range. You get a CSV. A few weeks later you ask again, for a range that overlaps the first one. Now you have two files that both contain your February.

The bank does not put an ID on any row. So when the same Netto purchase shows up in both files, nothing in the data says "these two lines are the same event." You have to work it out from the content. And that is where it gets nasty, because two identical lines are sometimes one purchase seen twice, and sometimes two real purchases.

The one sentence

Which rows across my overlapping export files are the same transaction — and how do I prove I got it right, given the bank gave me no IDs?

Get it wrong one way and you double-count your spending. Get it wrong the other way and your two coffees on Friday become one, and 45 kr quietly evaporates. Every rule in these two PRs is an answer to that sentence.

02

What the CSV gives you, and what it doesn't

After this: you know which three things are missing and why that's the root of everything.

Eight columns. That's the whole raw material.

ColumnWhat it is
DatoThe purchase date — not the date the bank recorded it. Module 03 is entirely about this.
TekstFree text. "Netto 8721", "Kaffebar", "Rejsekort". Sometimes has double spaces in it.
BeløbThe amount, with a Danish decimal comma.
SaldoYour running account balance after this row. Recalculated every time the bank makes a file.
StatusUdført (done) or Slettet (deleted before it was ever booked).
Kategori, UnderkategoriThe bank's own guess at a category. Space-padded. Kept, never trusted.
AfstemtAlways Nej in every file you have. Ignored.

The three things that aren't there

  • No transaction ID. Nothing identifies a row as a specific event. This is the whole problem.
  • No account. The file doesn't say which of your accounts it is. You tell the system that at import time.
  • No currency. Same — it comes from your account settings, never from the file.

So the system only ever knows what account a file belongs to because you told it. That's why one of the manual decisions in Module 08 is "I imported this against the wrong account, undo that."

03

Two dates that are not the same date

After this: you can explain why a month you thought was finished can still grow.

You buy coffee on Tuesday 31 March. The café's terminal settles on Thursday. The bank books it on 2 April — but it writes Dato = 31-03-2026, the day you actually bought it.

Two consequences, and they cause about half the trouble in these PRs:

  • That purchase lands in March. Not April. So your March total changes after March is over.
  • A file made on 1 April cannot contain it. The bank hadn't booked it yet. Only a file made on 3 April or later shows it — and when it does, it appears on 31 March, on a date your earlier file already "covered".

The system calls this a late booking. It is completely normal, not an error.

Why this matters for everything downstream

When a newer file shows a transaction your older file didn't, that is not evidence the files disagree. It's the expected shape of the data. The rules have to allow it — which is exactly what Module 07's "explained growth" is for.

04

Bronze, Silver, Gold — who is allowed to do what

After this: you can say which layer a given rule belongs in, and why the split is enforced.

Three layers. The whole point is that each one is forbidden from doing the next one's job.

LayerThink of it asDoesMust never
Bronze A photocopier Keeps the exact bytes forever. Splits them into rows. Records which account you declared and when the file was made. Interpret anything. No trimming, no number parsing, no dedupe.
Silver A librarian Turns text into dates and decimals. Maps Udført → booked. Works out which rows are the same transaction. Checks the balances add up. Assign household meaning — no categories, no budgets, no "this is a transfer".
Gold The report table One row per booked transaction, categorised, ready for the dashboard. Correct or fill in a balance. It carries numbers, it never fixes them.

The reason for the strictness: Bronze keeps the original bytes, so if you later find a parser bug, you re-run Silver over the same bytes and get a corrected result. Nothing is ever lost, because Bronze never edited anything in the first place.

Everything in Modules 05–08 happens in Silver. That's where the whole argument lives.

05

Giving a transaction a name that never moves

After this: you can explain the ID formula and why two obvious alternatives were rejected.

This is ADR-009, the most important document in the stack. A transaction's ID is a hash of five things:

IngredientExample
accountyour everyday account
transaction date2026-03-20
amount-45.00
identity textKaffebar — trimmed, double spaces collapsed to one
occurrence k1 or 2 — see below

What k is for

You bought two identical coffees on the same day. The file shows:

Export A — two genuinely different purchases
DatoTekstBeløbk
2026-03-20Kaffebar-45,001
2026-03-20Kaffebar-45,002

Without k, both rows hash to the same ID, the system says "duplicate", collapses them, and you lose 45 kr. With k, they're two distinct IDs. k counts look-alike rows within one file, top to bottom.

Two ideas that were rejected — and you should know why

"Use the row's position in the file." The same coffee is row 7 in Export A and row 12 in Export B. Its ID would change the moment a newer file arrives. Your category, your note, your correction — all of it detaches and points at nothing.

"Include the balance after the transaction." Worse. A late-booked purchase on the 19th makes the bank recalculate every balance after it. So a coffee on the 20th gets a new balance, therefore a new ID, even though nothing about the coffee changed.

The rule to remember

Your categories and corrections hang off these IDs. An ID that moves is worse than no ID at all. Everything ADR-009 rejects, it rejects for that reason.

06

The balance chain is your lie detector

After this: you can read a Saldo column and say whether the file is trustworthy.

Since the bank gave you no IDs, you need some other proof that a file is complete. The Saldo column is it. Each row's balance should equal the previous row's balance plus this row's amount. That's the balance chain.

A healthy chain — every line checks out
DatoTekstBeløbSaldoCheck
2026-03-19Netto-120,001.249,50—
2026-03-20Kaffebar-45,001.204,50✓ 1.249,50 − 45,00
2026-03-20Kaffebar-45,001.159,50✓ 1.204,50 − 45,00
2026-03-21DSB-36,001.123,50✓ 1.159,50 − 36,00

Now a broken one:

A broken chain — the file is not telling you everything
DatoTekstBeløbSaldoCheck
2026-03-20Kaffebar-45,001.204,50—
2026-03-21DSB-36,001.098,50✗ expected 1.168,50 — off by 70,00

70 kr went out and the file doesn't show what it was. The bank is counting a row it isn't exporting to you. That file cannot be trusted as evidence, so the rule (ADR-010) is to set the entire file aside — quarantine it — rather than import a version of your March that is quietly 70 kr wrong.

Good news, checked against your real files

The prototype ran your actual exports: 0 out of roughly 900 balance links break, and the single blank Saldo is on a Slettet row, which the chain correctly skips. The chain rule holds on your real data today.

07

A file gets admitted whole, or not at all

After this: you can explain "explained growth" and why half a file is never imported.

When a new file arrives, it is admitted only if both of these hold:

  1. It still shows every transaction already admitted for the dates it covers. Nothing has gone missing.
  2. Its end-of-day balances differ from the ones already on file by exactly the total of the transactions it adds.

Rule 2 is called explained growth. Worked through:

Export A (made 14 Feb)Export B (made 1 Mar)
Rows on 12 FebNetto −120,00Netto −120,00 + Rejsekort −200,00
Balance end of 14 Feb3.480,003.280,00
Difference−200,00 — exactly the Rejsekort that B adds. Explained. ✓ admit B

The Rejsekort was bought on 12 February and booked on 16 February — a late booking (Module 03). B is right, A was right when it was made, and nothing is wrong.

If the difference had been −250,00 instead, nothing accounts for the extra 50 kr. That's an unexplained difference: the file is quarantined and a review item lands on your desk.

Why never half a file

Because the balance chain only proves anything as a whole run of rows. Import the good half and the arithmetic no longer ties out, so you've thrown away the one proof you had. All or nothing.

08

The four times a human has to decide

After this: you know every case where the system stops and asks you something.

The system refuses to guess. When it can't settle something by rule, it quarantines and waits. There are exactly four rulings you can record — and the fourth one is new in PR #31.

DecisionYou're sayingWhen
void import run "I imported this file against the wrong account." Your mistake at import time.
same transaction "These two rows are one purchase; the bank reworded the text." The bank changes Tekst, so the ID formula sees a new transaction.
withdrawn "The bank removed that one. The newer file is correct." A newer file shows fewer copies of a repeated transaction.
accept discrepancy new in #31 "The bank's own numbers don't add up and never will. Take the file anyway, and mark those months honestly incomplete." A permanent balance-chain break (Module 06).

Crucially, a manual decision never edits the source data. It's recorded alongside it, and re-running the whole import from scratch replays your decisions and gives the identical result. Your rulings are inputs, not patches.

09

Coverage — how a dashboard tells a comfortable lie

After this: you can spot the single most dangerous failure mode in the whole system.

Every account × month gets one of three coverage labels:

LabelMeans
completeEvidence spans the whole month and every balance link checks out. If the total is 0, that is a proven zero.
partialThere's data, but there's a gap or a broken link. Don't trust the total.
no dataNo evidence reaches this month at all. The system has nothing to say.

And separately, a period can be provisional: it may still change, because late bookings are still landing in it (Module 03).

The one rule that matters most

no data must never render as "you spent 0 kr."

"I have no idea what happened in February" and "I have proof you spent nothing in February" look identical on a chart — both are an empty bar. One of them is a lie that will make you think you're doing better than you are.

Hold onto this. Two of PR #31's seven fixes (C3 and C7) exist purely to stop the dashboard making this exact mistake — and one of the still-open review comments says it can still happen. That's Module 12.

10

What PR #31 actually fixed

After this: you can say what each of C1–C7 was, without re-reading the PR.

PR #16 wrote the rules. Someone then built a working toy of those rules and ran them. Seven things broke. PR #31 fixes those seven and ships the toy as evidence. Here they are, roughly worst first.

C1The order you import files in changed your data
Symptom
Import A then B → 25 transactions. Import B then A → 20 transactions, and two weeks of February gone. Same two files.
Cause
Files were admitted in the order you fed them in. The older file A can't show a purchase booked after A was made — so arriving second, A looked like it was hiding something, and got quarantined.
Fix
Admit files in the order the bank made them, not the order you imported them.
C3A file of old history claimed to reach today
Symptom
You download all of 2025 on 15 April 2026. The filename ends -20260415, so the system concludes the file's evidence reaches 15 April 2026. Result: January, February and March 2026 read complete · zero. The dashboard says you spent nothing in February.
Cause
One date was doing two jobs: when the bank made the file and how far the file reaches.
Fix
Two separate fields. exported_on = when it was made. covers_through = how far it reaches, which you declare at import. Those months now read no data.
C4One bad day locked out a window forever
Symptom
A balance break on 5 March quarantines that file — correct. But every later file covering 5 March breaks identically, because the bank recalculates Saldo the same wrong way every time. 1–10 March is permanently unreachable. None of the three existing manual decisions could touch it.
Cause
Quarantine had no exit for a break that's real and permanent in the source.
Fix
The fourth decision, accept discrepancy. The file is admitted, the break is recorded and never repaired, and those months stay honestly partial.
C7"Provisional" came off too early — three ways
Symptom
The rule was "wait for a file made 7+ days after the month ends". A file made 8 April but starting 1 April qualifies — yet it structurally cannot contain a 31 March purchase booked on 2 April. March was declared final on evidence that couldn't possibly contain what we were waiting for. Also: an account you never imported held every month provisional forever; and a quiet account with no new activity could never clear the label at all.
Cause
Three separate holes in one rule.
Fix
The qualifying file must also cover the period's last day; no_data accounts don't hold the label; a re-exported identical file still records its own date.
C6Two documents gave opposite instructions
Symptom
Two coffees on 20 March; a later file shows only one. ADR-009 said "keep the higher count, raise a review item" — which reads like accept the file. Issue #5 said quarantine it. The prototype showed accepting is incoherent: the coffee you insisted on keeping has no slot in the new balances, so the chain breaks and March flips complete → partial.
Fix
Keep the quarantine. A withdrawn decision clears it and admits the file with the chain intact.
C2Two documents defined the ID differently
Symptom
domains/transaction.md said to include the row's position in the file. ADR-009 said the opposite (Module 05). Under the old text, 6 of 15 IDs moved when a second file arrived.
Fix
transaction.md now just points at ADR-009 instead of defining a competing rule.
C5Three details nobody had written down
Symptom
Is -45,0 the same amount as -45,00? Does a non-breaking space count as whitespace? Is k counted before or after trimming? The third one was nasty — counting on untrimmed text produced two different transactions sharing one ID.
Fix
ADR-009 now states all three: amount quantised to two decimals, whitespace means any Unicode whitespace including 0xA0, and k is counted on the trimmed text.
Note
None of these bite your current files — but one of your real exports has 176 rows with double spaces inside the text, so the whitespace rule is already load-bearing.
11

Driving the dashboard without getting lost

After this: you can open the prototype and get something out of it in ten minutes.

The file is prototypes/import-identity/identity-merge.prototype.html. Double-click it. Nothing is saved; reload and it's blank again. It's a throwaway toy, not code to build on.

What you're looking at

Almost every screen is two panels side by side, and that's the key to the whole thing. The left panel runs the rules as PR #16 wrote them. The right panel runs them with PR #31's fix. You are meant to compare, not to read.

  • The yellow bar at the top lists exactly what differs between left and right. The same differences are highlighted yellow inside both panels. If you read nothing else on a tab, read the yellow bar.
  • Each panel, top to bottom: the files you imported (green = accepted, red = quarantined) → any review items raised → the months × accounts grid with the provisional row under it → the transactions that survived.
  • "Rule set" at the top of each panel expands to show every switch that's on. It says proposed rules when nothing is changed from PR #31's defaults.
  • Buttons: Run all does every import at once. Next step goes one at a time — use this when a result surprises you. Reset clears.

A ten-minute path

  1. Open the Issue #5 baseline tab. Confirm it says 17 of 17 pass. This is your sanity check — the original acceptance scenarios still work under the new rules. Don't bother reading the individual scenarios.
  2. C1 → press Run all. Both panels are PR #16 as written; one imported A-then-B, the other B-then-A. Watch 5 transactions vanish and a file go red. Then press Fixed: A→B vs B→A: no differences at all. That's the headline result of the whole PR.
  3. C3 → preset H alone: as written vs fixed. Left: three months of 2026 marked complete · zero from a file containing only 2025. Right: no data. This is Module 09's lie, on screen.
  4. C7 → preset Missed late booking: as written vs fixed. Left says March is final. Right says provisional. Small difference, real consequence.
  5. C4 → preset As written vs the "accept discrepancy" decision. Left: 1–10 March gone for good. Right: recovered, and still honestly partial.

That's the tour. C2, C5 and C6 are worth clicking through only if Module 10's summary of them didn't land.

Free play takes your own CSV. It asks which account, the export date if the filename has no -YYYYMMDD suffix, and optionally the range end. Cut-down versions of your real exports are in imports/mwe/ (gitignored — nothing real is committed).

12

The ten review comments, and what #32 did about them

After this: you know which comments would have bitten you during implementation, which are now closed, and which are tidy-ups.

Ten review comments were raised on PR #31. Here they are in plain words, sorted by what they'd actually cost you. All ten are now closed — four in PR #32, the remaining six in the follow-up this page ships with. Each says what the fix actually was, so you can check the fix rather than take it on trust.

The dashboard can still lie to you

presentation-layer.mdThe current month can still render as finalfixed in #32

PR #31 added: accounts with no_data don't hold the provisional label. Sensible — an account you never imported shouldn't make every month provisional forever. But no_data also covers an account you did import, just not recently enough.

Concretely: it's 16 September and you last imported through August. Every account is no_data for September → no account holds the label → September renders as final. The current, still-accumulating month, shown as settled. That's precisely the failure this PR exists to prevent.

Fixed in #32: a period containing the current month always carries the label, no exceptions. The exemption now applies only to closed periods, and is written on "this account has never been imported" rather than on the coverage status — which is the thing that was actually meant all along.

bronze-layer.mdThe C3 fix is opt-in, and silently falls backfixed in #32

covers_through is something you declare at import. Declare nothing and it silently falls back to the export date — which is exactly the old behaviour C3 removed. The only stated validation is that it can't be later than the export date.

So: forget to declare it once on a year-of-history download and C3's bug returns in full. A mistyped-but-plausible date is accepted silently too — too early truncates your evidence, too late manufactures confirmed zeros over months the file never covered. The suggested minimum: refuse a covers_through earlier than the last transaction date in the file, since the file demonstrably reaches at least that far.

Fixed in #32: three rules replace the bare fallback. A declared date outside [last transaction in the file, export date] is refused, never quietly corrected. The declaration is required in the cases where the fallback would be wrong. Only otherwise does it fall back — and it records that it did, so you can always tell which happened.

ADR-006A leftover line still states the thing C3 removedfixed in #32

ADR-006 still lists "the export date is trusted as the extent of an export" as an accepted consequence. That's the C3 behaviour, left standing as a recorded decision. Cheap to fix, confusing if left.

Fixed in #32: removed, and folded into the fix below rather than left as a follow-up — a recorded consequence that contradicts the new formula would have made the two documents disagree the moment the formula landed.

Two documents still disagree

silver-layer.mdGold can't compute evidence_through from what Silver hands itfixed in #32

Silver passes a single date per account. Gold then has to choose between "that date" and "the day before the export date" — which needs to know the export date of the run that date came from. That value never crosses the boundary. The hand-off exists in prose only.

And: four documents state this rule in four different wordings, with a real ambiguity between them — is the answer "take the max, then adjust" or "adjust each, then take the max"? Those give different answers. An implementer will just pick one, and the four documents will drift apart from day one. The suggestion: state the formula once, per-run then maxed, and have the other three cite it.

Fixed in #32: exactly that. silver-layer.md states the formula once — adjust each file, then take the maximum, with the reason that order is the right one — and Silver now hands the computed value across the boundary as a named field instead of leaving Gold to re-derive it. The other three documents cite it.

silver-layer.mdA new qualifier appears in one document and not the otherfixed

The architecture doc now says balances are compared "only on dates where both state one." ADR-009 still states the admission condition without that qualifier — and the line traces to none of the seven claims. It's the same divergence C2 was about, in a different pair of documents. Either it's real and belongs in ADR-009 with its reasoning, or it was defensive and should go.

Fixed: it turned out to be neither — it's a consequence, not an exemption, and ADR-009 now says why. A date only gets a balance once it has a transaction on it. If the old data has one for a date and the new file covers that date, the new file must have one too, or it was already thrown out. The only other case is a date that's brand new in the file, where everything on it is new money — counted at the next date they both have, with the file's own internal chain joining the dots. Nothing goes unchecked; only the date the check lands on moves.

ADR-009"Import order doesn't matter" is slightly overstatedfixed

The tiebreak for two files the bank made on the same day is started_at — which is import order. So two same-day files with different ranges can still admit differently depending on which you feed in first. The claim just needs scoping to "files produced on different days."

Fixed, and tested rather than argued. The claim is scoped to different days, and the prototype was run on same-day pairs to find out what actually happens. Two files the bank made on the same day showing the same state: identical either way, ticks all round. Two files where the bank booked something between them: you still end up with the same transactions and the same IDs, but feeding the newer one in first quarantines the older one and holds back any dates only it reached — until you void the newer run and re-import it. That's written down now, including the way out.

Why it can't be fixed properly: the bank stamps its files with a date, not a time. Two files made the same day are genuinely indistinguishable in order. This is C1's bug surviving inside a single day, at the one resolution the evidence doesn't have.

A decision nobody will ever find

ADR-010accept discrepancy never appears in your work listfixed

A balance break raises a validation error, not a review item. Review items are what show up as "something for you to decide." So accept discrepancy is the one manual decision with nothing prompting it: the file is quarantined, every later file covering that date is quarantined for the same reason, and you'd have to already know this escape hatch exists to use it. Given that the whole point of C4 is the permanent case, a third review-item kind would make it discoverable.

Fixed: a broken chain now raises a review item — a third kind, balance break — as well as the errors. So it lands in your work list like the other two, and the decision has something to attach itself to when you make it. You can see it in the prototype's C4 tab, in the new settled by column.

Bugs in the prototype itself

prototypeTwo look-alike groups on one date can collidefixed

If two coffees and two teas on the same day both drop their second occurrence, both synthesised positions compute to the same number — which breaks a uniqueness rule Gold relies on. Not hit by any shipped scenario.

Fixed, and it mattered more than "prototype bug" suggests. The old numbering added the repeat counter to the row count, so both landed on 4. Run the reviewer's example and you got positions 1, 2, 4, 4; now you get 1, 2, 3, 4. The real finding is that the documents never said how to number these at all — so any implementer would have invented the same colliding scheme. The rule is now written into silver-layer.md, and the prototype grew a collision badge for it.

prototypeWithdrawn transactions counted asymmetricallyfixed

One check excludes withdrawn transactions, a neighbouring one doesn't, so re-importing a group after withdrawing one of its instances under-reports the growth. Latent; no scenario reaches it.

Fixed: the code was comparing against two different pictures at once — what you believe is true, and what the stored balance actually reflects. Those come apart the moment you record a withdrawn decision. So if the bank later showed that purchase again, the file got quarantined for an "unexplained" balance that was perfectly explainable. The two pictures are now separate and labelled as such.

bronze-layer.mdOne new sentence isn't actually backed by the evidencefixed

"A declared range end after the export date is refused" is never enforced in the prototype. It doesn't corrupt any result — a too-late value falls through to a safe fallback — but that specific sentence isn't covered by the "17 of 17, 7 of 7" the PR description leans on.

Fixed — and this is the one you should actually read about. Enforcing the rule proved the rule was wrong. See module 14.

The one worth taking away

The previous version of this page told you the three prototype comments needed no action, because the prototype is throwaway and had already produced its evidence. That was right about two of them and wrong about the third.

"This rule isn't enforced in the prototype" is a different kind of comment from "this code has a latent bug." A latent bug is a path nobody walks. An unenforced rule means nobody has checked whether the rule works — and when it finally was checked, it didn't. Module 14 is that story, and it's the most useful thing on this page.

My honest read

Merge the stack. All ten comments are closed.

These PRs are documents, not code. Nothing ships when you merge them; they're the decisions you'll build from. And the unusual thing here is that somebody actually ran the rules before writing them down and found seven real defects. That's much stronger evidence than you normally get from a docs review — "we'll find the pitfalls during implementation" is what you'd be settling for, and #31 already did better than that.

Three of the ten comments were the ones an implementer could not route around: they'd have had to invent an answer, and the documents would then have been wrong. PR #32 makes exactly those three fixes, plus the ADR-006 leftover that would have contradicted one of them:

  1. The no_data provisional exemption — it made the current month render as final whenever you were behind on imports. That's the exact class of bug this whole stack exists to prevent. Now the current month always carries the label.
  2. evidence_through stated four ways and not computable from Silver's output — an implementer would have picked one reading and the four documents would have diverged immediately. Now stated once, and the value crosses the boundary.
  3. The covers_through silent fallback — the C3 fix was opt-in, so one forgotten declaration brought the bug back at full strength. Now bounded, sometimes required, and it records when it fell back.

The remaining six are closed in the follow-up this page ships with: three documents that disagreed with each other, and three findings in the prototype. One of those six turned out to matter much more than its tag suggested — module 14.

What "merge" buys you here: nothing ships. These are documents — the decisions you'll build from. The unusual thing is that somebody actually ran the rules before writing them down. "We'll find the pitfalls during implementation" is the alternative, and it's strictly worse than what you already have in front of you.

One thing worth saying plainly: you don't need to hold all of this in your head. You need to be able to recognise a wrong answer when the dashboard shows you one. Module 09 is the test that catches almost everything — if a month you never imported ever shows up as a confident zero, something upstream is broken, and you'll now know roughly where to look.

14

The rule that was wrong until somebody ran it

After this: you know why "we wrote it down carefully" is not the same as "we checked it", and what that's worth in practice.

This module exists because of one review comment that looked like the least important of the ten. It said: the documents say a declared range end after the export date is refused, but nothing in the prototype actually checks that. Tagged "no action" in the last version of this page — my mistake.

What the first fix said

Module 12's covers_through fix needed a rule for when you must declare the range end rather than letting it default. The reasoning went: if the last purchase in the file is long before the date the bank made the file, that's the shape of a history download, and defaulting would be wrong. Seven days felt right — it's already the late-booking window used elsewhere.

It reads perfectly well. It was wrong.

The moment the rule was actually implemented and the seventeen test scenarios were run against it, five of the seventeen were refused. Not edge cases — five perfectly ordinary imports, of the kind you'd do every month.

Why it broke

Take the simplest one. You download February on 1 March. Your last purchase that month was on 13 February, because nothing happened in the last two weeks — a completely normal quiet fortnight. That's a 16-day gap, so the rule demanded a declaration.

But there was never any danger there. Remember from module 03: a file made on 1 March proves nothing about 1 March, because the day is still booking — so the system already pulls the evidence back to 28 February on its own. Which is exactly right. There was nothing to protect against, and the rule was demanding paperwork for it anyway.

Counting days was the wrong question. A quiet tail at the end of a month is normal. What's actually dangerous is something else entirely.

The right question

Ask what the guess would claim, not how big the gap is

Defaulting means claiming evidence up to the day before the file was made. So: does that reach into a later month than the last purchase in the file?

February file, made 1 March, last purchase 13 February → the guess reaches 28 February. Same month. Safe, no declaration needed.

All of 2025, downloaded today → the guess would reach yesterday, claiming eight months of "we checked, nothing happened" that the file never covered. Different month. Declare it.

That's the rule now. All seventeen scenarios pass again, and the history download is still refused without a declaration — which was the whole point. Same protection, none of the false alarms.

What this is actually worth to you

You asked at the start whether you had to accept these PRs and find the pitfalls during implementation. Here's the concrete answer:

  1. A carefully-reasoned rule was wrong. Not carelessly written — it cited the right window and gave a plausible justification. It was still wrong.
  2. Nothing in a document review would have caught it. It reads fine. It only fell over when something ran it against real scenarios.
  3. The cost of catching it here was about an hour. The cost of catching it in implementation would have been you, staring at a refused import of your own February statement, wondering what you did wrong.

That's the case for the prototype in one paragraph. It isn't there to be good code — it's throwaway. It's there so that a sentence someone wrote confidently gets the chance to be proved wrong before you build on it.

The thing to remember

When a review comment says "this rule isn't actually enforced anywhere", that is never a small comment. It doesn't mean there's a bug. It means nobody knows whether the rule works, and the confidence you have in it is borrowed from how well it's written.
