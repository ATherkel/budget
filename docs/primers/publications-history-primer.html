Why did February change — and can I see it as it was?

Issue #8 decides what one build of Gold is, which build a report reads, what is kept of past builds, and what “reproducible” actually promises. Contents

01

The one question behind all of it

After this: you can state what issue #8 exists to decide, in one sentence.

On 5 March you open the dashboard: February groceries 520.00. On 15 June you look again: 820.00, and the IKEA purchase you remember as household goods now sits under gifts. Nothing in your bank data was edited. Both numbers were right when they were shown.

Two different things moved. More data arrived (a late booking), and your interpretation changed (a manual decision, a rule, a renamed category). The warehouse is designed to restate history — every dimension is Type 1, and classification re-runs from scratch on every build. That is a feature: last year’s numbers get better when your rules do. But it raises three questions a household will eventually ask:

  1. Which version of February am I looking at right now?
  2. Can I see the version I saw on 5 March, exactly?
  3. How much of the change was new data, and how much was me re-deciding things?

The one sentence

Every report is a function of recorded inputs — so record them, name each result, and let the household pick which result it reads.

02

“Gold is reproducible from Silver” was false

After this: you can list what a Gold build really reads, and name the one thing it must never read.

Principle 3 used to say Gold is reproducible from Silver. Count what a Gold build actually consumes:

InputWho changes itExample change
Silver transactionsimportsa late booking appears
Account registryyou, in a fileBo’s account gets imported
Category taxonomyyou, in a filerename streaming
Classification rulesyou, in a fileadd r-net
Manual decisionsyou, by commandIKEA → gifts
Matching policy + codethe developera faster matcher

Only one of six is Silver. So the principle now reads: Gold is reproducible from its recipe — all six, each named exactly.

The one forbidden input: the clock

If a build ever asked “what is today?”, two builds of identical inputs could differ, and you could never prove a rebuild matches. So a build never reads the clock, file timestamps or environment variables. built_at is still recorded — as metadata about the result, never part of it. That is how the ticket’s worry about created_at timestamps dissolves.

What about things that genuinely depend on today, like the provisional label on the current month? Presentation computes them when the report is read, which it already did.

Check yourself: why can’t the managed period end at “this month”?

Because that reads the clock. The contract ends an open account’s managed period at the latest month present in the published data instead — the same rule, applied back in #6.

03

A publication: one complete build, read one at a time

After this: you can say what a publication is, and why a consumer must never read two.

A publication is one complete, immutable build of Gold: every account and category row, every transaction and allocation, the monthly snapshots, lineage and review items. Each gets a publication_id — P1, P2, … — and once stored it never changes.

Several publications can sit in the store at once (module 09 says which). That creates the classic warehouse trap the ticket warns about: double counting.

February expenses in four retained publications (June 2026).
PublicationWhat it isFeb expenses
P6current3,349.00
P5previous (for undo)3,349.00
P1labeled “March review”3,049.00
P7labeled “Known 5 March”3,049.00
naive SUM(amount) over the whole table12,796.00

The defence is structural, not a coding convention. Every Gold table is keyed by publication_id first. A GoldRepository is bound to one publication when it is opened, and no method reads across two. Analytics can’t write the wrong sum because it is never handed the rows to write it with.

Facts do not carry publication_id — analytics has no business knowing it. A consumer that wants to show which build it is reading calls repository.publication().

04

The recipe, and the fingerprint that checks it

After this: you can name a recipe’s parts and say what a matching fingerprint proves.

Every publication carries a recipe: what it was built from, named exactly, never “latest”.

PartFor P3 in the running example
Dataimport runs run-1 and run-2, each with its payload hash
Configuration snapshotfingerprint c1: accounts, taxonomy, rules, matching policy — parsed, canonical
Decision-log positionentry 1 (IKEA → gifts)
Code versioncommit k1, with its locked dependencies
Result fingerprintSHA-256 over every record the publication returns, in key order

The first four parts are the cause; the fingerprint is the effect. The promise is: the same recipe, rebuilt with the same code, gives the same fingerprint. Three steps of the running example lean on it.

Three builds that test the promise.
WhenWhat you didOutcome
04-12deleted the bad rule againrecipe equals the current one → nothing is built
05-03verify: full rebuild from Bronze, in a scratch areafingerprint equals P5’s → reproducibility proven, nothing published
06-01upgraded the code, no intended behavior changenew publication P6, same fingerprint as P5 → the upgrade provably changed nothing

The snapshot is of parsed configuration, so reformatting a file or restoring a rule you deleted gives the same fingerprint. And because the recipe names the code, production refuses to build from uncommitted changes — it could not say what built the result.

Check yourself: a code change gives a different fingerprint. Is that a bug?

Not necessarily — it is attributable. The recipe names both code versions, and the diff (module 05) shows exactly which numbers moved. What would be a bug is the same recipe and code giving two fingerprints.

05

Switch at once, print the diff, undo in one step

After this: you can walk through the NETFLIX mistake from build to undo.

Current is a pointer. The dashboard reads whatever it points at. A successful build stores its result and moves the pointer in one SQLite write transaction, so a reader sees the old publication or the new one, never half of each. A failed build — say, a decision naming a category that doesn’t exist — leaves everything as it was.

The mistake

On 12 April you add r-net: text contains NET → groceries. You meant NETTO. It also matches NETFLIX.COM, where it disagrees with r-streaming at equal priority, so that transaction turns unknown with a rule-conflict (ADR-011). The build succeeds and P4 goes live — and the CLI prints:

Diff P3 → P4, as the terminal shows it (never written to logs).
MonthMeasureChange
2026-02streaming−129.00
2026-02Expenses−129.00
2026-02unclassified out−129.00 (1)
review items+1 rule-conflict

That is your cue. undo points current back at P3. The pointer history records both moves:

P1→ P2→ P3→ P4→ P3

Undo changes no input. The bad rule is still in your file, so the next build would bring it back — you still fix the rule. Undo just buys you a calm moment, and it is itself undoable: after undo, P4 is “the previous one”.

Check yourself: why is “switch at once” safe without a review gate?

Because the previous result is always retained, so going back is instant, and the diff puts every moved number in front of you at the moment you made the change. A gate would catch the same mistake one command later, on every single import.

06

Two clocks: what you knew, and how you read it

After this: you can place current, as-was and as-known-at on a two-axis grid.

Every report answers two questions, and each answer is a point in time. Which data? — cut at when each import ran. Which interpretation? — configuration, decisions and code. Kimball’s name for this is bitemporal.

ViewDataInterpretationFeb groceries
Currenteverything so fartoday’s820.00
As-was 5 Marchimported by 5 Marchin force on 5 March520.00
As-known-at 5 Marchimported by 5 Marchtoday’s520.00

The payoff is in comparing them. Each pair differs on exactly one axis:

  • Current vs as-known-at — same interpretation, different data. The 300.00 difference is purely the late booking that arrived on 10 March.
  • As-was vs as-known-at — same data, different interpretation. The differences (IKEA moved to gifts, streaming renamed and regrouped) are purely you re-deciding things.

Why cut data at import time rather than the bank’s export date? The export date says when the bank made the file, not when you knew about it. An export produced on 1 March that you imported on 20 March was not known on 5 March.

Check yourself: what about the fourth corner — today’s data, March’s rules?

Not offered. Rule files are only read when a build runs, so “the rules on some date” is only known at the moments a publication was built. It could be offered at those points later; the first release does not.

07

As-was: exactly what you saw

After this: you can explain how an as-was view is found, and when it needs old code.

view --as-was 2026-03-05 --label "March review" looks up the pointer history: which publication was current on 5 March? P1. Then one of two things happens:

  1. P1’s result is still retained → it is simply labeled, and the dashboard can open it.
  2. It isn’t → P1’s recipe is replayed under the same publication_id, and the replay must match P1’s recorded fingerprint. P1 was built by code k1 and you now run k2, so the CLI refuses and names k1 as the version to replay with.
February in P1, as seen on 5 March.
CategoryGroupAmount
groceriesfood520.00
household-goodshome2,400.00

Note the old category name and group. That is why ADR-007 could choose Type 1 dimensions without losing history: each publication carries the dimension rows as they were. Type 2 would have preserved what streaming was called, but not that the IKEA purchase was then household goods — the reinterpretation lives in the facts, and the publication keeps those too.

category-changes.md still matters: the publication shows what the categories were; the log says why they changed.

08

As-known-at: old data, today’s eyes

After this: you can predict what an as-known-at view shows, including its labels and review items.

view --known-at 2026-03-05 --label "Known 5 March" is a new build, P7, of kind as_known_at. It takes only the import runs started by 5 March (run-1; run-2 came on the 10th) and interprets them with today’s configuration, decisions and code. Silver is derived for that subset in a scratch area, so the live Silver is untouched.

February, as known on 5 March, read today.
CategoryGroupAmount
groceriesfood520.00
giftspersonal2,400.00
“Subscriptions”housing129.00
Expenses3,049.00

Three details worth predicting before you read them:

  • It can never become current. It is missing data by design.
  • February is labeled provisional. Past views take the label as of their own moment — known_at — not today. On 5 March no export produced 7+ days after February’s end had been imported, so February was still provisional then.
  • A decision can be “not applicable”. Had you recorded a decision about a transaction first imported on 10 March, this view raises decision-not-applicable for it — just as a build on 5 March would have.
09

Keep the recipe, not the cake

After this: you can say which results are kept, and what it costs to see one that isn’t.

A recipe is a few kilobytes. A result is every row of Gold — a few megabytes after some years of data. Every recipe is kept forever. Results are kept only for:

  • the current publication;
  • the previous one, so undo is instant;
  • every labeled one, until you remove the label.
P1 · label P2 P3 P4 P5 · previous P6 · current P7 · label

Dashed: recipe only. Green: result kept. Filled: current. June 2026, after both views.

Anything dashed can be re-created by replaying its recipe with the code it names. Two honest limits:

  • Code rots. A recipe replays only while its code still runs. If a publication must outlive its code — a tax year, say — label it, so its result is kept.
  • Schema changes. ADR-013 lets a Gold migration drop and rebuild Gold tables, and those tables now hold the kept results. So a Gold migration either converts them or deletes them. The recipes survive either way, but an old-contract publication can then only be replayed with its own code, into a separate store.
10

The decision log: nothing is ever edited

After this: you can change and retract a decision without editing anything.

Every manual decision — classifying a transaction, settling a review item, voiding an import run — is an entry in one append-only log. The platform stamps recorded_at when it accepts the entry; you never type it.

Changing your mind about IKEA, twice.
EntryRecordedDecisionKindSupersedesEffective afterwards
104-10d-0001classify C → gifts—C is gifts
207-02d-0007classify C → household-goodsd-0001C is household-goods
307-09d-0008withdrawd-0007no decision: r-home decides

The effective decisions at entry n are those recorded up to n and not superseded up to n. That is what lets a recipe say “decisions up to entry 1” and mean something exact forever.

ADR-011 says a transaction has at most one decision. With a log, a second decision on C that doesn’t name supersedes is rejected when you record it, not discovered at the next build. That validation boundary is the one a future browser editor reuses (issue #10).

Rules, taxonomy and accounts stay ordinary edited files. Their history is the configuration snapshots inside recipes.

Check yourself: why is a withdraw entry needed at all?

Because deleting entry 2 would rewrite history: a recipe pointing at “up to entry 2” would silently change meaning. Withdrawing is a new fact about a new moment, so old recipes stay exact.

Which identifiers survive a rebuild

After this: you can say what names “the same transaction” and what names “one version of it”.

IdentifierStable across publications?Why
account_id, category_idalwaysimmutable household keys, never reused
transaction_idwhile ADR-009’s identity version holdsderived from content + occurrence
allocation_id, transfer_group_id, review_item_idwhile the same inputs produce themderived from the ids above
account_sequencenoordering only; shifts with late bookings
(publication_id, transaction_id)names one version of one factthe only way two versions differ

So the IKEA purchase is the same transaction in P1 and P6 — same transaction_id — and your decision can target it forever. What differs is its version: household goods in P1, gifts in P6.

One page, one publication

A dashboard page makes several requests (HTMX loads panels separately). If a build finished between two of them, one panel could show P5 and the next P6. So the page opens the current publication once and carries that publication_id in its follow-up requests. A page never mixes two builds; reloading picks up the new one.

12

What you decided, and what was decided for you

After this: you know which choices were yours, and which ones to check.

Your five choices

  1. Past reports come as as-was and as-known-at, beside current. (modules 06–08)
  2. Keep every recipe; keep results for current, previous and labeled. (module 09)
  3. A successful build goes live at once, with a printed diff and one-step undo. (module 05)
  4. Manual decisions live in an append-only log. (module 10)
  5. Views are built by the CLI and opened by the dashboard, which stays read-only. (modules 07, 08)

Decided by the agent — please check

module 03One database, not a file per publication

Every Gold table is keyed by publication_id, so the pointer moves in one SQLite transaction. This answers the question ADR-013 left open for #8.

module 02The build never reads the clock

Anything that depends on today is computed when a report is read.

module 04Production refuses uncommitted code; identical recipes publish nothing

A development build may run from uncommitted code; its publication is marked not reproducible.

module 06Data is cut at import time, not the bank’s export date
module 08Past views are provisional as of their own moment
module 09Gold migrations can delete kept results

This refines ADR-013’s drop-and-rebuild allowance. Recipes survive; old-contract results need their own code to replay.

module 06Correction: the fourth corner is not free

Corrected. It was first described as falling out for free. It doesn’t, because rule files are only read at build time, so it is left out.
