# D1: Specify immutable monthly budget inputs and reporting history

Part of: https://github.com/ATherkel/budget/issues/100. First-release delivery plan.

Blocked by: #101

## Problem Statement

Read-only monthly budget comparison is now in the first release, but the old architecture describes budgets as future work. Resolve how externally maintained plans become reproducible reporting inputs.

## Solution

Maintainer-approved budget contract, schema/versioning proposal and independent expected outcomes are ready for #12. Contract drafting itself requires no application TDD.

## User Stories

1. As a household member, I want missing targets distinguished from zero, so that comparison remains honest.
2. As an operator, I want historical reports to retain their plan, so that editing today's budget cannot rewrite an As-was comparison.
3. As a maintainer, I want one budget source and scope model, so that future rådighedsbeløb and reserves can extend it coherently.

## Implementation Decisions

- Translate the parent's confirmed authoring, household-scope and historical-plan decisions into a minimal validation and publication contract. No live mutable budget-file reads from the dashboard.
- First release: household targets in TOML and exact declared account-scope comparison. Account-specific budgets are a confirmed deferred requirement: carry scope identity/membership explicitly and centralize applicability so later account plans do not require presentation rewrites. Defer their overlap/precedence policy rather than guessing.
- Specify stable category/group references, DKK exact monthly targets, duplicate/invalid/retired references, explicit zero, missing months and partial-plan completeness. Do not infer completeness from omission.
- State how a plan becomes part of a Publication's recipe/result and allowed public Gold projection. Reconcile analytics-only-Gold and Gold-only dashboard storage; amend accepted architecture through an ADR if necessary.
- Confirmed history: target edits take effect in a new Publication; an As-was view keeps original targets; an As-known-at view captures the plan used when that view is built. Specify how this works without mutating existing Publications.
- Specify account membership changes and exact matching of selected accounts to plan scope, known-at/as-was semantics, stale/legacy plan versions and clear unavailable reasons.
- Provide finite synthetic examples including target edit, old versus new Publication, subset of accounts, missing month, explicit zero, and partially budgeted categories.
- Reserve a coherent extension path for planned income/commitments in #99 without implementing or deciding its fixed/other policy; do not implement a generic planning engine.

## Testing Decisions

- The same pinned Publication and context returns the same targets after the external input file is edited.
- Incomplete category targets do not become a falsely complete total budget.
- A changed plan produces an explicitly different published comparison while the prior As-was result stays reproducible.

This is contract/specification work: use reviewable synthetic examples, not application tests or implementation disguised as documentation. Obtain maintainer decisions explicitly.

## Out of Scope

Budget editor, forecasts, automatic target inference, earmarking/carry-forward and fixed-expense implementation.
