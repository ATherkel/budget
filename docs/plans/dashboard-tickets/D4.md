# D4: Add category investigation and reusable detail navigation

Part of: https://github.com/ATherkel/budget/issues/100. First-release delivery plan.

Blocked by: #104

## Problem Statement

Let readers investigate a Category without putting every transaction on the overview, and establish one reusable accessible detail interaction.

## Solution

On-demand Category investigation works from the simple overview with coherent context and accessible reusable detail behavior.

## User Stories

1. As a reader, I want to open a spending heading and see contributing entries, so that I can understand its amount.
2. As an operator, I want allocation amounts rather than repeated whole-transaction amounts, so that the detail remains correct at the accepted grain.
3. As a keyboard user, I want predictable close/back and focus return, so that investigation does not trap navigation.

## Implementation Decisions

- Implement category/group detail reports and compact displayed rows using allocation identity and amount, with original transaction identity/amount only where explanatory.
- Show current-month and year-to-date detail with explicit scope; use the same refund and Coverage meanings as D3.
- Build one on-demand detail module reused by categories and later account/check details; use ordinary navigation as a fallback if enhanced disclosure is unavailable.
- Keep Publication/accounts/period and comparison-mode state through open/close; switching to Enkel dismisses advanced detail.
- Return empty/unknown/unavailable states without inventing transactions. Never expose source IDs, private lineage or raw bank account identifiers.

## Testing Decisions

- An expense refund reduces the category detail total and appears with its correct sign and period.
- Allocation rows agree with analytics totals; tests do not assert private template structure.
- Open, close, back, Escape when a dialog is used, and focus return work at phone width and by keyboard.

Use the agreed public HTTP/rendered-page and analytics-report seams. Each behavior follows one focused red test → maintainer review → green implementation → separate review/refactoring.
